Loop Engineering

A 5-stage self-improving prompt loop — Inspect → Build → Verify → Red Team → Improve — for any AI task where a single pass isn't reliable enough.

When to use this

Any task handed to an AI assistant where a single prompt-and-accept pass isn't reliable enough: drafting a deliverable against a brief, generating code against a spec, producing analysis that has to hold up to scrutiny. Tool-agnostic by design — nothing below depends on a specific product.

The shift this procedure encodes: stop treating a prompt as a one-shot question. Treat it as a loop that checks its own output and rewrites until the output clears a bar, then feeds what it learned back into the next run.

The 5 Stages

Stage 1
Inspect

Before generating anything: pin the goal, constraints, source files, output format, and success criteria. A bad Stage 1 produces a correct answer to the wrong question — this is the step most commonly skipped.

Stage 2
Build

Generate one full draft from the Stage 1 context. This is a draft, not a final answer. Resist the urge to negotiate over a partial answer.

Stage 3
Verify

Check the draft against the brief: Did it follow instructions? Is the logic solid? Is the format correct? Compliance check, not a quality judgment.

Stage 4
Red Team

Attack your own output before a critic does: what is weak, what could fail, what would an adversarial reader attack first? Run this as a separate pass from Verify — merging them produces a shallow pass that only catches easy problems.

Stage 5
Score, Rewrite, Repeat

Score against the Stage 1 success criteria. If it doesn't clear the bar, rewrite with Stage 3/4 findings folded in. Cap at 3 passes — if there's no material improvement, surface what's unresolved rather than declaring success.

The Portable Prompt Template

Paste this as a system or instruction block ahead of the actual task. Works in any tool — no plugins, no code execution, no vendor dependency.

system prompt / instruction block 
You are running a 5-stage loop on this task. Do not skip stages or merge
them into one pass — complete each stage's checklist before moving to the
next, and show your work at each stage rather than jumping straight to a
final answer.

STAGE 1 — INSPECT (before generating anything)
Read the brief/files/goal and state explicitly:
- Goal: what does "done" mean here?
- Constraints: what am I not allowed to change or assume?
- Files/inputs: what source material actually exists?
- Tone/format: what does the output need to look like?
- Success criteria: how will this be judged?
If any of these is missing or ambiguous, say so before proceeding.

STAGE 2 — BUILD
Generate the first full output from the Stage 1 context.
This is a draft, not a final answer.

STAGE 3 — VERIFY
Check the Stage 2 output against the brief:
- Did it follow the brief?
- Is the logic/reasoning solid?
- Is the format correct?

STAGE 4 — RED TEAM
Attack your own output before a critic does:
- What is weak?
- What could fail?
- What would a critic attack first?

STAGE 5 — SCORE, REWRITE, REPEAT
- Score the output against the Stage 1 success criteria (1–10 or pass/fail).
- If it doesn't clear the bar: rewrite, folding in Stage 3/4 findings.
- Repeat Stages 3–5 until it clears the bar or you've made 3 passes without
  material improvement — if the latter, stop and say explicitly what's still
  unresolved rather than declaring success.

Report at the end: the final output, the score, and what Stage 4 flagged
that you did or didn't fix and why.

Running It Manually

  1. Inspect first, every time. Write down goal / constraints / files / format / success criteria even for a task that feels obvious.
  2. Build one full draft, not a partial answer to negotiate over.
  3. Verify and red-team as two separate passes. Verify checks compliance with the brief; red-teaming looks for what an adversarial reader would attack. Merging them produces a shallow pass.
  4. Score against the Stage 1 criteria specifically — not a vague sense of quality. If Stage 1 didn't produce concrete success criteria, fix Stage 1 first.
  5. Cap the rewrite loop. Three passes without material improvement is the signal to stop and surface what's unresolved, not to keep iterating silently.
  6. Improve the system, not just this output. After the loop closes, log what broke and fold the fix into whatever governs the next run — a checklist, a skill file, a saved prompt. The same failure shouldn't have to be red-teamed again next time.
In Claude Code: The task-loop-runner agent already implements Stages 2–5 (act → evaluate → retry) for a single well-defined task with a checkable success condition. Stage 1 (Inspect) and Stage 6 (fold the fix into a durable skill) are still worth doing explicitly around it, since those are what prevent the same failure from recurring.

What Each Stage Catches

Stage What it catches Common skip mistake
1 – Inspect Wrong framing, ambiguous brief, missing inputs Jumping to Build with an unclear goal
2 – Build First-pass gaps, structural issues Partial draft treated as negotiation starter
3 – Verify Failed instructions, format errors, logic breaks Merged with Red Team into one shallow pass
4 – Red Team Adversarial weaknesses, attack surface Skipped because the draft "looks good"
5 – Score Whether the output actually clears the bar Unbounded rewrite loop with no exit condition
