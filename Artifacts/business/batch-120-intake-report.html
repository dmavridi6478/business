1. Executive findings

  • [Certain] The pgvector carousel leaves out the one thing that breaks multi-tenant apps. It calls filtered search "the real superpower", but with approximate indexes the filter is applied after the index scan, so a query can return fewer rows than LIMIT. pgvector 0.8.0 added iterative index scans for this (hnsw.iterative_scan). I checked this against the pgvector README and put it in the skill, with row-level security for tenant isolation.
  • [Certain] The "passive income" prompts and the "5 AI prompts" are generic, and the framing is marketing. Nothing here is passive: every stream needs setup, support, maintenance and marketing, and the model cannot see real demand. I kept the prompts verbatim and added validate-first rules and a ban on income claims.
  • [Certain] The Cowork sales prompts feed customer emails, files and call transcripts to an AI service and ask for browser research of named people. The graphic does not mention data-protection, recording consent, anti-spam rules or LinkedIn terms. The "5+ hours a week" figure is unmeasured. I added the checks and a rule to draft but never auto-send.
  • [Certain] The second "50 Claude use cases" list does not duplicate the existing one: it is organised by Claude surface (Excel, PowerPoint, Chrome, Cowork, Claude Tag, Claude Design). I added it as a reference to claude-50-use-cases. Which plan each product needs was not verified.
  • [Certain] OpenMausBot is the riskiest repo here. It is days old, formerly OpenGrokBot, and its agents can use a desktop, a VM or, on opt-in, your own computer plus 500+ apps through a connector service. Happy gives remote control of coding agents (1,081 open issues). Openreplay records user sessions, which needs consent and masking. Each has a care note.
  • [Certain] I searched GitHub for the apps on the cards. Stars and licences were read from the repo pages; for OpenMausBot the page count was not returned, so I quote the card's 5,599 as the card's.

4. Where I disagree with the source material

  • I disagree that a Postgres WHERE clause is enough for tenant isolation. The risk is cross-tenant leaks and silently short result lists. Use row-level security and test recall.
  • I disagree with "passive income" as a goal for prompts. The risk is building assets before demand exists, then repeating income claims. Validate first, with stop criteria set in advance.
  • I disagree with pointing an agent at a whole Drive and inbox. The risk is leaking customer data and acting on hallucinated facts. Use one folder, name sources for every claim, and send nothing automatically.
